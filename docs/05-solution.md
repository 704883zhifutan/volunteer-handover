# 05 · 设计方案：只读核对工具（志愿者排班与交接）

> 面向评审与交付的方案说明。代码级取舍见 [design.md](design.md)；数据契约见 [api.md](api.md)；
> 报价见 [04-quotation.md](04-quotation.md)；事实来源见 [01-discovery.md](01-discovery.md)。

---

## 1. 目标与非目标

**目标**（可验收）：

1. 把"排班表 / 签到 / 交接记录"之间对不上的地方，变成**一页带坐标的清单**（`文件#L行号`）。
2. 让交接有**责任清单**：版本状态、未结项、归属、截止时间。
3. 让"有没有改善"可复算：误报率、确认完整率、召回率、核对工时。

**非目标**（写进合同，不因客户要求而改）：

- 不写回任何系统、不发外部消息、不自动指派（尤其医疗/安保）。
- 不判定"交接是否完成"（G3 未定义）。
- 不替代现场指挥与人工判断，不做实时接入。

## 2. 五条设计原则

| 原则 | 落到哪里 | 反面教训 |
|---|---|---|
| **只判定，不修复** | 没有任何写接口；建议统一以"仅提示"开头（有测试断言） | 一旦能改，错误就会被改得看不出来 |
| **每条结论可回溯** | 无 locator 的结论直接丢弃 | 无法核对的条目会让整页清单失去信任 |
| **没核实的数不填** | `backfill_threshold_minutes: null`；不预设"迟到多久算超时" | 编一个阈值，等于把假设当事实 |
| **失败即标记** | 读不到文件 → 快照标 unavailable + 明确"这不等于没有缺岗" | 一次误判能造出 8 条假缺岗（已修复的真实 bug） |
| **能力边界在代码里** | `core/boundary.py` 8 项禁用能力，命中即 blocked | 边界写在提示词里，换个模型就失效 |

## 3. 总体架构

```
输入（只读导出）                处理                        产物
┌──────────────┐                                    ┌──────────────┐
│ positions    │──┐                                 │ items.md/csv │ 一页缺项清单
│ shifts       │  │   ┌───────────────────────┐     │ handover.md  │ 交接责任清单
│ checkins     │──┼──▶│ loader（快照+表头契约）│     │ metrics.*    │ 三个指标
│ handover     │  │   └───────────┬───────────┘     │ diff.*       │ 批次对比
└──────────────┘  │               ▼                 │ snapshots    │ 读到什么
                  │   ┌───────────────────────┐     │ audit.csv    │ 谁做了什么
 review.csv ──────┼──▶│ checks C1–C9 + 交接清单│────▶│ score.md     │ 金标比对
 gold_overlap.csv ┘   └───────────┬───────────┘     └──────────────┘
                                  ▼
                        human_queue（人判断：L1 核对 / L2 确认）
```

**技术形态**：单机 CLI，Python 3.9+ 标准库，零第三方依赖，不联网、不建库、不起服务。
这不是"简化版"，而是刻意的：客户能在自己的隔离环境里跑，审计时能整包带走。

| 模块 | 职责 | 关键文件 |
|---|---|---|
| 加载与契约 | 只读读取、sha256 快照、缺列阻断 | `core/loader.py` `core/schema.py` `core/trace.py` |
| 判定 | C1–C9 九条确定性校验 | `core/checks.py` |
| 产物 | 一页清单、交接清单、指标、对比 | `core/items.py` `core/handover.py` `core/metrics.py` `core/diff.py` |
| 复核与金标 | 回填、召回率 | `core/review.py` `core/gold.py` |
| 边界与配置 | 禁用能力、配置白名单 | `core/boundary.py` `core/configschema.py` |

## 4. 数据契约

| 文件 | 性质 | 关键列 | 为什么需要 |
|---|---|---|---|
| `positions.csv` | 字典 | position_id / category / site_id | 判断岗位类别与要求点位 |
| `shifts.csv` | **计划类** | shift_id / person / window / confirm_status / version_no / 有效期 | 版本有效性、占位冲突 |
| `checkins.csv` | **事件类** | checkin_id / shift_id / person / site / 双时间 / source_tool | 现场与计划是否一致 |
| `handover.csv` | **事件类** | 接收人 / 签收时间 / 版本 / open_items | 交接责任链 |
| `review.csv` | 回填 | 编号 / 结论 / 复核人 / 时间 | 没有复核人与时间的结论不生效 |
| `gold_overlap.csv` | 金标 | 班次对 / 是否真重叠 / 标注人 | 召回率的分母 |

两条硬约定：**计划类记录不判"时间倒挂"**（否则排班表会刷出一片假异常）；**缺失值 ≠ 未确认值**（三值逻辑）。

## 5. 九条校验：各自抓什么、明确不做什么

| 编号 | 判定 | 不做 |
|---|---|---|
| C1 | 排班 vs 签到：缺岗、点位/人员不一致、计划外到岗 | 不判断"是否真缺岗"，只说明两边对不上 |
| C2 | 同一人时间窗重叠且岗位不同 | 同岗位连班不算冲突 |
| C3 | 双时间倒挂、疑似回填（批量来源） | 不预设延迟阈值 |
| C4 | 版本断链/过期/未确认 | 不替人决定"用哪版" |
| C5 | 交接：未签收、接收人缺失、同一人交接、版本不符、未结项无主/逾期/编号重复 | 不输出 `is_complete` |
| C6 | 已确认却有空洞（缺失与未确认混同） | 未确认行交给 C4，避免重复计数 |
| C7 | 重复编号、断链、时间窗倒置、单位差异 | 不改写原行 |
| C8 | 读取失败 | 不重试、不补值、不编造 |
| C9 | 配置中出现禁用能力 | 不"尽力而为"，直接 blocked |

## 6. 人机四层与四个签字

```
L0 系统：只提示（"仅提示，不执行"）
L1 当班人：核对原始行（现场事实只有现场知道）
L2 业务负责人：确认生效（清单不生效不得进现场）
L3 人工队列：判定不了就排队，不默认通过；必要时暂停试点
```

| 签字 | 谁 | 缺了会怎样（代码行为） |
|---|---|---|
| 复核回填 | 复核人 | 缺复核人/时间 → 该条**不生效** |
| 清单确认 | 顾明岚（L2） | 无确认 → 不进现场 |
| 门禁放行 | 傅景 + 顾明岚 + 叶书 | `deploy.sh` 退出码 3，拒绝出包 |
| 对外口径 | 叶书 | 系统本就没有发送通道 |

## 7. 指标与验收

| 指标 | 定义 | 分母 | 门槛 |
|---|---|---|---|
| S1 召回率 | 金标真重叠中被工具找到的比例 | 金标真重叠对数 | W3 目标 100%（G1） |
| S2 误报率 | 被驳回的占已复核比例 | **已复核**条数 | 先测基线，不预设 |
| S3 核对工时 | 每批次人工核对小时数 | 批次数 | 必须低于现状（唯一硬约束） |
| S4 返工次数 | 同一事项被重复处理次数 | 批次 | 不升 |
| S5 确认完整率 | 已复核条目 / 全部条目 | 全部条目 | **100%（硬门）** |
| S6 必要复核保留率 | 必要人工确认被保留的比例 | 应复核条目 | **100%（硬门）** |
| S7 队列负荷 | 每日进队列条数 | 日 | 有人值守（G2） |

S5/S6 是硬门，理由：效率提升如果靠"少核对"换来，就是拿风险换数字。

## 8. 实施路线与门禁

| 阶段 | 内容 | 出口 |
|---|---|---|
| W0 | 事实台账、假设、失败方式表、门禁草案、桌面推演 | 三门禁有草案；G1 判定方法确定 |
| W1 | 数据地基薄版：四表契约、快照、C1/C2/C5 先落 | 单批次能跑通 |
| W2 | 清单进现场，只开 3 个环节 | 连续两周无假状态 |
| W3 | 回放 50 次调班做金标（双人标注） | 召回/精确可复算 |
| W4 | 复盘决策门 | 扩 / 收 / 停 + 下一轮报价 |

**三门禁（不关不开工）**：G1 判定方法与人 · G2 队列值守与叫停 · G3"完成"的定义。详见 [gates.md](gates.md)。

## 9. 主要风险与缓解

| 风险 | 表现 | 缓解 |
|---|---|---|
| 假状态 | 文件没读到却报"没有缺岗" | C8 + 可用性判断 + "不等于没有缺岗"警告（已修复过一次） |
| 越界 | 配置里出现写回/外发/指派 | C9 + 边界测试（源码扫描 import） |
| 误报泛滥 | 一周后没人看清单 | 一页上限 40 条；超了报警告而不是加页 |
| 口径漂移 | 同一指标两种算法 | 指标从落盘 CSV 复算，口径写死在代码里 |
| 归因之争 | "效率提升"算谁的 | 只对核对工时分浮动；其余不进公式 |
| 无人值守 | 队列堆着没人处理 | G2 未关不放行（停止条件之一） |

## 11. 与报价的对应

33 人天里，约 40% 花在"让人愿意相信结论"这件事上（金标、双人标注、门禁、可追溯、审计）。
这部分不产生界面和功能，但它决定了清单能不能进现场。报价单里每一项都能在仓库中找到实现，
客户可以自己跑一遍 `bash scripts/build.sh` 来验收，而不必相信一份文档。
