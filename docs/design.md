# 设计说明

本文回答四个问题：为什么切这么小、九条校验凭什么算"确定性"、哪些东西被刻意留在代码外面、
以及还有哪些没弄清楚的地方被写成了占位而不是默认值。

---

> 上游看 [workflow.md](workflow.md)：人的流程摊开、按出错代价排序；本文从那里往下，
> 讲"为什么这九条校验、而不是别的校验"。

## 1. 问题形态：不是六个功能，是两件产物 + 两个数据前提

访谈里六个角色各提了需求，很容易被读成六个要开发的功能。但把它们摊开看，形态是这样的：

| 需求 | 实质 | 处理方式 |
|---|---|---|
| REQ-1 交接责任清单 | 产物 | 代码（`core/handover.py`） |
| REQ-2 缺项清单 | 产物 | 代码（`core/items.py` + `core/checks.py`） |
| REQ-3 双时间戳 | 数据前提 | 字段契约 + 校验（`core/times.py`） |
| REQ-4 跨工具关联编号 | 数据前提 | 候选规则 + 校验（`core/ids.py`） |
| REQ-5 验收与抽样 | 方法 | 不写代码，写进验收表 |
| REQ-6 人工队列 / 暂停 | 流程 | 不写代码，写进 G2 |

所以仓库里只有两个"产品"模块。REQ-5、REQ-6 如果被做成功能，会在第一周就被绕过去：
真正的队列是群里那句"这个我去问一下"，不是工单系统里的一个状态。

## 2. 九条校验：为什么它们算"确定性规则"

"确定性"的判据是三条：**输入相同则输出相同**、**不依赖模型判断**、**每条结论可回溯到行**。
凡是需要"看情况""大概是""我觉得"的地方，一律不做。

| 编号 | 名称 | 拦的是什么失败 | 判定依据 | 为什么不做成"智能判断" |
|---|---|---|---|---|
| C1 | 交叉比对 | F1 缺岗没登记、F2 排班表与现场不一致 | 排班 ± 签到 ± 岗位点位三者比对 | 谁真的缺岗要现场确认，代码只能指出"两边对不上" |
| C2 | 占位冲突 | F3 同一替补被排到两个点位 | 同一人员代号 + 时间窗重叠 + 岗位不同 | 重叠是算术事实；要不要改派是人的决定 |
| C3 | 双时间单调性 | F4 回填时间被当成发生时间 | 接收 ≥ 发生；批量来源额外标记 | 阈值未核实，所以只标记不判定（见 §5 H1） |
| C4 | 版本有效性 | F5 过期版本覆盖已确认新版 | 有效期区间 + 确认状态 + 是否被替代 | 文件名、修改时间都不可信，只有这两个字段可信 |
| C5 | 确认链完整 | F6 有结论没确认人、未结项无归属 | 签收人、未结项责任人、截止时间 | "算不算完成"是业务定义（G3），代码不判定 |
| C6 | 三值逻辑 | F7 缺失被当成已知 | 已确认 + 关键字段为空 | 三值必须显式，不能靠空字符串兜底 |
| C7 | 编号唯一与闭合 | F8 重复编号、孤儿引用、单位差异 | 编号集合运算 + 时间窗实算 | 单位差异能算出来，所以不需要"猜" |
| C8 | 失败即标记 | F9 读取失败被"补"出数据 | 快照状态 = unavailable | 宁可这次没结论，也不能给假结论 |
| C9 | 能力禁用 | F10 越界写回 / 指派 | 配置项非空即报 | 边界只能被"挡住"，不能被"承诺" |

C1 和 C2 的异常类型受配置白名单约束（`scope.allowed_anomaly_types`），因为现场类误报
会直接吃掉人的时间。C3–C9 属治理类，关掉它们等于关掉追溯，所以始终启用。

### 为什么 C3 不对"晚 3 分钟"报警

第一版实现在这里踩过坑：把排班记录的 `received_at`（计划录入时间）和 `window_start`
（班次开始）比较，得到 10 条"时间倒挂"——全是误报。**计划类记录本来就写在班次之前**，
接收早于发生是正常的。

修正后的规则分两类：

- **计划类**（`shifts.csv`）：不判倒挂，只在"记录晚于班次开始"时标记疑似回填；
- **事件类**（`checkins.csv` / `handover.csv`）：要求接收不早于发生，否则两个时间戳必有其一不可信。

这条修正写进了 `checks.PLANNED_FILES` 和 `tests/test_checks.py`，不是一次性的手动排除。

## 3. 字段契约

三条硬约定，任何新增字段都必须服从：

1. **三值**：有值 / 缺失 / 未确认。空字符串永远算"缺失"，"未确认"必须显式写出来。
2. **双时间**：`occurred_at`（业务发生）与 `received_at`（系统接收）分开存，口径以发生为准。
3. **版本**：`version_no` + `version_valid_from/to` + `confirm_status` + `superseded_by`；
   作废必须写 `void_reason`，不许删除原行。

缺项清单的每一行都带 `来源位置 = 文件名#L物理行号`。这不是给人看的描述，是坐标系。

## 4. 刻意留在代码之外的东西

| 留在外面 | 理由 | 谁来补 |
|---|---|---|
| 异常优先级排序 | 排序隐含价值判断，第一周就该由业务方改 | 顾明岚 |
| "完成"的判定 | 定义未确认（G3） | 顾明岚 + 唐映秋 |
| 编号最终规则 | 只是候选规则（H5） | 待确认责任方 |
| 延迟阈值 | 事实未核实（H1） | 秦芮测完再说 |
| 队列与叫停的执行 | 是流程不是功能（G2） | 傅景 + 唐映秋 + 林亦舟 |
| 对外沟通措辞 | 不自动对外承诺 | 叶书 |

代码里对应位置：`core/handover.py` 没有 `is_complete`；`config` 的
`backfill_threshold_minutes` 是 `null`；`core/ids.py` 的 `build_shift_id` 注释写着"候选"。

## 5. 未关闭的门禁与待核实假设

**这三个不关，工具不进现场**（明细、证据要求与签字栏在 [gates.md](gates.md)；`scripts/deploy.sh` 读它，有一个未勾就拒绝出包）：

- **G1** "发现全部重叠"怎么判、谁判、抽样还是全量 —— 傅景 + 秦芮
- **G2** 人工队列谁值守、多久响应、谁能暂停 —— 傅景 + 唐映秋 + 林亦舟
- **G3** "完成"是否包含交接确认 —— 顾明岚 + 唐映秋（叶书确认客户侧）

**六个假设仍是假设，代码里以占位形式存在：**

| 编号 | 假设 | 现在怎么处理 | 核实后改哪里 |
|---|---|---|---|
| H1 | 导出更新频率 / 晚多久算延迟 | 阈值 `null`，只标批量来源回填 | `config` 的 `time.backfill_threshold_minutes` |
| H2 | 留存与调阅期限 | 未实现自动清理，快照全留 | `core/trace.py` |
| H3 | 删除虚构个人字段的约定 | 样本数据全部虚构，无真实姓名 | `data/` |
| H4 | 谁批准例外处理 | 无批准入口，写进审计备注 | 不实现，走人工 |
| H5 | 编号规则由谁定 | 只提供候选规则 | `core/ids.py` |
| H6 | 投诉与差错的归口 | 无对外通道 | 不实现，走人工 |

## 6. 已知取舍

**一页上限 40 条。** 超了不追加页，而是报警告（`ItemSheet.page_warning`）。理由：一页装不下
说明筛选规则错了，加页只会让人不看。这条规则有测试守着。

**配置解析器是 YAML 子集。** 只为免掉第三方依赖，支持嵌套映射、标量列表、注释、`null`。
不支持锚点、行内非空集合、跨行字符串。遇到不支持写法抛 `ConfigError` 带行号，不静默降级——
配置静默降级比崩溃更危险。

**建议文案统一以"仅提示"开头。** 有测试断言。这不是文案洁癖：一条写成"已将 Z0007 改派"
的建议，第二天就会有人以为系统真改过。

**审计日志写本地，不发送。** 它是证据文件，不是消息通道。

## 7. 变更规则

1. 动 `FORBIDDEN_CAPABILITIES` 需要审核与质量负责人书面同意。
2. 新增校验必须同时加：失败方式说明（本文 §2 表格）、对应单元测试。
3. 改字段契约必须同步 `docs/api.md`、`data/` 样本、`CHECK` 测试。
4. 样本数据是金标：`tests/test_engine.py` 断言 20 条缺项、3 条交接。改数据就要显式改测试，
   顺手改了却没过测试说明逻辑被动过。

## 8. 闭环：清单发出去之后怎么办（0.2.0）

0.1.0 能把"对不上的地方"找出来，但找出来之后没有下文：清单里的复核状态永远停在"未复核"，
于是 S2 误报率、S5 确认完整率都没法算，W4 复盘只能靠印象。0.2.0 补三处，都是为了让结论可证伪。

| 补的东西 | 解决什么 | 不补会怎样 |
|---|---|---|
| `data/review.csv` 回填 | 人工结论回到系统，误报率有分子 | 每周重跑一遍，判断不留痕 |
| `core/schema.py` 表头契约 | 缺列 → 阻断；缺可选列 → 跳过并告警 | 缺一列会造出一页看起来合理的假缺项 |
| `data/gold_overlap.csv` 比对 | "发现全部重叠"有了分母 | 这句验收永远无法判定真假 |

三条判断值得记下来：

1. **误报率的分母只能是"已复核"**。用全部条目当分母，未复核就被当成"不是误报"，
   数字会随着人越懒越好看。
2. **金标未覆盖不算误报**。工具报了、没人标过这一对，正确做法是补标注，而不是收窄条件——
   否则我们会为了压精确率把真问题一起关掉。
3. **条目编号用内容指纹，不用序号**。序号随检查顺序漂移，复核结论会挂错条目；
   内容指纹的代价是数据一变编号就变，旧结论需重新确认，而"变了就重核"本来就是对的。

顺带修掉一个真缺陷：同一交接的两条信号（未签收 / 交出人与接收人为同一人）此前共用
`校验+类型+对象+位置+双时间`，算出同一个编号，人工回填只能落在其中一条上。
现在 `detail` 参与指纹计算，`tests/test_review.py` 断言同一次运行内编号唯一。

## 9. 堵掉"静默"（0.3.0）

0.2.0 让结论可证伪，0.3.0 处理另一类更难看见的问题：**错误不报错，只是悄悄少了一部分结果。**

三条都属于同一族（F9 假状态）：

1. **配置拼错 = 关掉一类校验。** 把 `require_confirm_status` 打成 `..._staus`，代码读到 `None`，
   "版本未确认"整类异常消失，而清单只是"干净了一些"。现在未知键直接 blocked，并给出最像的键名。
   宁可打断人一次，也不要让人以为自己看的是全部。
2. **顶班被当成数据错误。** 签到里有、排班表里没有，以前报"编号断链"——语义错了：
   断链是数据问题，顶班是现场事实，两者的处理人不同。现在由 C1 报"计划外到岗"，
   断链只留给交接记录（那里确实只可能是编号错）。
3. **同一交接里 `OI-1` 出现两次。** 谁负责、结没结都成了两说，而两行各自看起来都"格式正确"。
   现在单独报"未结项编号重复"，不合并、不取第一条。

另外补了批次对比（`--baseline`）。它依赖前面那个决定：编号是内容指纹。所以比对键不能用编号，
得用「校验 + 类型 + 对象」这组业务身份；编号变化单独标成"持续（内容有变）"。
否则同一件事补充了点位，会被读成"消失了又新增"，复盘时看不出它其实一直在。

**刻意没做的**：不做优先级排序（没有可靠权重，排出来的序会假装精确）、
不自动关闭"消失"的条目（那就是把"没看见"当"变好了"）。
